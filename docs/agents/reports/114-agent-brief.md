## Agent Brief

**Category:** component-proposal (enhancement)
**Summary:** Enable consumer-composed table actions through accessible header state, reusable sort icons and plain buttons; make Table horizontal overflow automatic and provide an independent ScrollContainer.

**Current behavior and verification:**
Source inspection of Table's implementation, public export, tests and stories confirms that Head and HeaderCell already accept children. HeaderCell exposes scope and alignment but cannot receive aria-sort. Root provides a named, keyboard-reachable horizontal scroll region only when notes is omitted; it has no bounded vertical scroll contract. Searches for sort state and scroll surfaces found no equivalent public component. Dialog, Sidebar and MultiSelect own specialized scrolling rather than a reusable container. Button supports primary, secondary and ghost: ghost remains padded, rounded and styled with button typography and a hover underline. It does not supply the accepted plain treatment. No public Icon primitive is currently exported.

These are verified missing public contracts from source inspection, not reproduced runtime defects. No runtime tests were run during triage. The prior-rejection knowledge base contains no rejection of this capability. The Figure-width and Brandmark-size decisions caution against invented size roles; this contract introduces none. The focus-boundary decision requires the shared focus ring rather than a second focus treatment.

**Accepted decisions:**
The maintainer approved the following, superseding the original issue's Table-owned vertical scrolling and sort-action contract:

- Table automatically handles horizontal overflow without an opt-in. Table does not own vertical height bounds or vertical scrolling.
- A reusable ScrollContainer can contain arbitrary content and uses space allocated by its parent layout. It has no arbitrary height/width or size-scale props.
- ScrollContainer exposes `axis?: 'both' | 'horizontal' | 'vertical'`, defaulting to `both`. Scrolling is available only when content overflows an enabled axis. Content wraps normally; remaining overflow on a disabled axis is clipped.
- All sorting belongs to consumer code: active column, direction changes, local ordering, backend requests and asynchronous response state. Table has no `onSort$`, sort-direction stream, data registry or sorting policy.
- Table.HeaderCell exposes consumer-supplied `ariaSort` as accessibility metadata. Existing children compose the header label, action and optional icons. Do not add slots without a demonstrated composition gap.
- Button gains `variant="plain"`: inherited surrounding typography and text color; no button fill, border, radius, added padding, minimum width or automatic hover underline. Keep native button semantics, disabled operation and the shared visible focus ring. Ghost retains its separate quiet-but-styled treatment.
- Ship reusable visual icons for unsorted (up/down arrows), ascending (up arrow), and descending (down arrow). The consumer selects the icon and composes it inside the plain button. These indicators are required to complete the feature, not left to consumer-drawn substitutes. They carry no sorting behavior and are decorative for assistive technology when ariaSort communicates the current ordering.

**Key interfaces:**
- `Table.HeaderCell.ariaSort?: 'none' | 'ascending' | 'descending' | 'other'` maps to the header cell's aria-sort attribute. Omission leaves it absent; changing it never triggers an action or reorders content.
- `Table.Head` and `Table.HeaderCell` retain their existing children composition. A consumer places a plain Button inside a header cell and connects its existing `onClick$` output to consumer behavior.
- `ScrollContainer` is a new public component with children, the closed axis choices above, and an accessible naming contract. Implementation default: require either a nonempty accessible label or a reference to an existing heading, using the repository's naming conventions. Do not open arbitrary DOM-prop, className or style forwarding.
- `Button.variant` adds plain while keeping the existing props, including onClick$, disabled, type and ariaLabel. Plain is an explicitly accepted exception to the existing universal button-face typography/radius treatment; reconcile the public documentation and applicable ADR statements so they do not contradict this decision.
- Reusable icons must be publicly exported and usable independently of Table. Implementation default: a closed `Icon` component with `name: 'sort' | 'sort-ascending' | 'sort-descending'`. These names select drawings, not state or behavior. Render non-focusable, assistive-technology-hidden icons; meaningful standalone use must be named by the containing control or accompanying text. Inherit current text color and scale with the surrounding text. Reuse the library's existing inline SVG approach; no external icon dependency or arbitrary SVG/style forwarding is required. Only these three drawings are in scope.

**Accessibility defaults delegated by the maintainer:**
Ensure the scroll container itself is keyboard-reachable when overflow exists on an enabled axis, including with entirely static content. Use the shared visible focus ring and native scrolling; do not intercept descendant controls' keys or trap focus. Re-evaluate scrollability after layout/content changes without relocating existing focus. Avoid an extra tab stop when nothing needs scrolling. Provide an accessible name with appropriate semantics, without making every incidental scroll wrapper a region landmark. A named group is suitable for a generic wrapper; a landmark requires a meaningful page section. Table keeps its caption and semantic structure.

References: [W3C scrollable-content keyboard rule](https://www.w3.org/WAI/standards-guidelines/act/rules/0ssw9k/), [landmark guidance](https://www.w3.org/WAI/ARIA/apg/practices/landmark-regions/), and [sortable-table composition example](https://www.w3.org/WAI/ARIA/apg/patterns/table/examples/sortable-table/). These guide implementation; overflow-dependent focusability and the naming API are component design defaults, not claims that WCAG mandates those exact APIs.

**Acceptance criteria:**
- [ ] Table preserves caption, header scope, header/body associations and existing static content behavior. Every notes mode handles residual horizontal overflow automatically while preserving its current responsive note behavior. No vertical bound or vertical-scrolling opt-in is added to Table.
- [ ] Header ariaSort supports every specified value, updates and removal. A consumer example marks only the currently ordered column, places an ordinary plain Button in sortable headers, and leaves action-only headers without a sort control. Accessible metadata describes the displayed order, not the next requested order.
- [ ] Table never orders data or cycles state. In an example with delayed consumer response, activating the button leaves the current order and ariaSort unchanged until the consumer updates them. Consumer errors, loading policy and backend access remain outside Table.
- [ ] Plain Button inherits the header's text treatment and wraps naturally with content. It introduces none of the excluded button-face styling, including when disabled. Disabled remains visibly distinguishable using semantic tokens, cannot activate, and retains native disabled semantics. Pointer, Enter and Space activation retain Button's existing output contract; default type remains button. Focus is visible without a fill/border change.
- [ ] Existing primary, secondary and ghost behavior remains compatible. Plain is reusable outside tables and supports accessible icon-only use through the existing naming prop.
- [ ] The three public icons have distinguishable shapes rather than color-only or size-only differences. Consumer examples use all three with visible header labels and plain Buttons, omit sort indicators from non-sortable headers, and keep the icon synchronized with the consumer's current ordering. Icons add neither tab stops nor duplicate spoken names; the button label and header ariaSort supply accessible meaning. Verify contrast and visibility in light, dark and forced-colors modes, including visible focus around the composed label and icon. The ariaSort value `other` needs no fourth icon in this scope; consumers can supply descriptive text for custom ordering.
- [ ] ScrollContainer supports all three axes and the default, uses parent-supplied bounds, and does not invent a viewport bound when the parent provides no finite constraint. Public examples explain and demonstrate the required parent layout, including flex/grid shrink behavior.
- [ ] Content wraps normally. Disabled-axis overflow is clipped; enabled-axis overflow stays reachable. Document that consumers must provide content/layout that fits the disabled axis: clipping is not a way to make essential content or controls inaccessible.
- [ ] Scrolling remains keyboard-operable for static and interactive content, with visible focus and no focus trap. Resizing and content changes update scrollability. Native scrollbars remain usable. Test wide/tall content, long labels, no overflow and changes in overflow.
- [ ] Demonstrate a Table inside a vertically bounded ScrollContainer. The outer container handles vertical scrolling and Table handles horizontal overflow; neither introduces an inaccessible or redundant same-axis scroll surface. Keyboard users can reach controls and scroll both areas, and focus outlines remain visible. Sticky table headings are not required by this decision.
- [ ] Add behavior tests and Storybook examples for consumer-composed header actions with all three icons, accessible current order, plain Button, and standalone/nested ScrollContainer. Include independently composed icon usage. Verify actual overflow, wrapping, icon distinction, keyboard scrolling and visible focus in a browser; DOM tests alone cannot prove those outcomes. Follow repository test-first implementation standards.
- [ ] Run required lint, typecheck, tests, build and Storybook build. Update public contracts and examples. Coordinate with the row-activation work in #113 and action variants in #119 rather than overwriting those contracts.
- [ ] Publish through the normal release process and record the actual released version in the consumer ticket. Report implementation readiness and publication separately; triage does not constitute a release.

**Out of scope:**
Sorting algorithms, sort state machines, frontend/backend policy, filtering, pagination, row selection, virtualization, sticky-header guarantees, new size scales, responsive column sizing from #115, and icons beyond the three approved sort indicators. Do not add an external icon-provider dependency or migrate unrelated internal icons as part of this work.
