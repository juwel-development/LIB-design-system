## Agent Brief

**Status:** Approved by the maintainer for agent implementation.
**Issue:** https://github.com/juwel-development/LIB-design-system/issues/111
**Category:** component-proposal (new shared capability)
**Summary:** Add a separate `NumberInput` field that preserves numeric edits as text,
requests a decimal keyboard and keeps parsing and validation with the consumer.

**Current behavior:**

Input exposes text, email and URL kinds without a numeric keyboard hint. Slider
selects a value from a fixed operating range; Select chooses from predefined values.
None serves freely typed amounts and thresholds with blank and incomplete edit
states. Source inspection confirmed the gap at `2235675` (package 3.8.0). All 16
existing Input tests passed, including clearing without replacing the focused node.

The prior rejection of content-rule props (#95) remains binding. ADR 0009 permits
field kinds while reserving content validation for the consumer. This capability
does not reopen min/max/step, patterns, length caps or clamping.

**Desired behavior:**

Export `NumberInput` as a separate component, with the same field appearance and
label, optional/required presence, hint, invalid/error, disabled and test-hook
conventions as Input. Existing Input behavior stays unchanged.

Render a text input with decimal input mode. Preserve its entered single-line text
without numeric conversion, trimming, separator replacement, rounding, clamping or
keystroke filtering. Emit that text on user input. Empty text, `0`, `-`, `1.`, `1,5`
and `1.5` remain distinct. Arbitrary pasted text is retained so the consumer can
explain an invalid value; the numeric keyboard hint is not a validation rule.

The browser/device chooses the actual keyboard. Request a decimal separator along
with digits, but do not promise a particular layout, a minus key, or exclusion of
other characters. Integer-only domains still validate in the consuming app. No
steppers, spinbutton behavior, currency formatting or automatic localization ship.

**Key interfaces and state contract:**

- `NumberInput` is one public roster entry. Its props interface is exported from
  its own module according to the component standard, not separately from the
  public barrel. It does not import or wrap a sibling component to share internals.
- Required `label: string` and `name: string`; optional `required`, `optionalLabel`,
  `hint`, `invalid`, `errorMessage`, `disabled`, `placeholder` and `testId`, using
  Input's existing types and conventions. No speculative styling or attribute props.
- `defaultValue?: string` initializes the uncontrolled field, including static
  rendering. It is not a command to replace the current edit on rerender. Consumers
  restore saved text through this prop when mounting/remounting a field; retained
  mounted fields retain their current edits across ordinary rerenders.
- `onInput$?: Subject<string>` emits the current text for user edits, including
  typing, pasting and clearing by editing. The component never emits a parsed
  number, `NaN` or Infinity as a numeric value. Text spelling such values remains
  text for the consumer to judge.
- `reset$?: Subject<void>` is the existing inbound clear command: empty the same
  live node without remounting or deliberately moving focus. Do not emit an
  `onInput$` event for a programmatic clear. The consumer clears its own saved state
  alongside this command if that state must remain cleared after remounting.
- Native form reset follows the native uncontrolled default-value behavior and
  emits no user-input event. Document that this restores the form default, whereas
  `reset$` empties the field. Neither operation updates consumer-owned saved state
  automatically.
- Subscribe only to `reset$`; unsubscribe on source replacement and unmount. Never
  subscribe to the output, complete either stream, or define error/completion
  policy. No `value$`, controlled value prop or React callback prop is added.
- Disabled prevents user edits and output events; a programmatic reset may still
  clear the field. Rendering, remount initialization and changes to messages emit
  no input events.

**Parsing, forms and accessibility:**

The consumer decides whether text is blank, unfinished, invalid or a finite accepted
number, which decimal/grouping conventions it accepts, and when to show an error.
The component renders consumer-authored `invalid` and error text without preventing
invalid edits. It neither decides domain limits nor converts blank to zero.

Provide English and German stories with consumer-owned parsing examples. Each
demonstrates blank versus zero, an incomplete edit, a valid decimal in that example's
locale and rejected content. Examples must validate the whole string before numeric
conversion, reject non-finite results and avoid accepting a numeric prefix of invalid
text. Any integer-only or whole-dollar examples belong to consumer code, not the
component contract. Do not publish a parser or locale service as a new library API.

Static rendering must work without accessing browser globals. The native form
submits the text by name and required checks presence. It does not guarantee numeric
validity; the server must parse/validate on a no-JavaScript round-trip and return
consumer-authored errors. JavaScript consumers likewise own preventing invalid
submission. There is no hidden numeric coercion or synthesized numeric form value.

Associate the visible label, optional hint and rendered error correctly, with unique
IDs across fields. Retain the shared focus treatment and field presentation in both
themes. Expose textbox semantics; do not claim spinbutton semantics without its
interaction model. Every visible string is consumer-authored.

**Acceptance criteria:**

- [ ] Public consumers can import NumberInput and render the existing field anatomy;
  Input, TextArea, Select and Slider retain their public behavior.
- [ ] User edits preserve and emit distinct empty, zero, incomplete, dot-decimal and
  comma-decimal text. Invalid pasted text is neither truncated nor converted. Test
  repeated edits, replacement and clearing through observable DOM/event behavior.
- [ ] The control uses text semantics and requests decimal input mode, with no
  numeric validation attributes, automatic formatting or key filtering.
- [ ] Initial saved values, normal rerenders, consumer remount restoration, native
  form reset and `reset$` clearing follow the documented contract. Reset keeps the
  live node and its focus, produces no user event and cleans up subscriptions.
- [ ] Disabled, required/optional presence, consumer-driven invalid/error states,
  accessible names/descriptions and multiple instances work correctly.
- [ ] Static markup contains the name, default text, presence and associations;
  native form data retains the text, including decimal commas and invalid content
  for server-side validation. Show that numeric validity is consumer-owned.
- [ ] English and German examples demonstrate complete-string parsing, blank versus
  zero, incomplete edits, finite-result checks and consumer-authored feedback.
- [ ] Add public-behavior tests first under the repository's testing standard.
  Cover the input/output streams, replacement/unmount teardown and absence of
  synthetic input events. Do not assert on private state or recipe strings.
- [ ] Stories cover empty, zero, decimals, incomplete and invalid/pasted content,
  clear/restore, disabled, required/optional and both themes. Inspect editing and
  keyboard behavior in a browser; document any mobile/device validation not performed
  rather than presenting a jsdom attribute assertion as proof of a keyboard layout.
- [ ] Closed props, semantic tokens, recipe ownership and stream lifetime rules hold.
  Lint, typecheck, tests, package build and Storybook build pass. Include the agreed
  NumberInput definition in the domain glossary if absent from the implementation
  checkout, and document caller obligations alongside the component.
- [ ] Publish through the normal release process and record the actual released
  package version on #111. Merging alone does not unblock the consumer upgrade;
  verify publication before reporting a released version.

**Out of scope:**

- Extending Input's variant axis, changing other field contracts, or introducing a
  shared field wrapper or component-internal dependency across siblings.
- Min/max/step, integer-only constraints, patterns, length limits, numeric bounds,
  clamping, steppers, currency arithmetic, domain parsing and validation engines.
- Live value replacement streams, controlled-value APIs, React callback props,
  generic attribute bags, consumer CSS/styling escape hatches or localization services.

**Platform evidence:**

The HTML standard's Number state sanitizes invalid numeric values to the empty
string; decimal input mode instead requests a fractional numeric keyboard. A jsdom
value-assignment probe confirmed that `-`, `1.` and `1,5` are emptied by number input
value assignment and retained by text inputs. This was not a real-browser typing or
mobile-keyboard test.
