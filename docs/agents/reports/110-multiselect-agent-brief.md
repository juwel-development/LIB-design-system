## Agent Brief

**Status:** Approved by the maintainer for agent implementation.
**Issue:** https://github.com/juwel-development/LIB-design-system/issues/110
**Category:** component-proposal (new shared capability)
**Summary:** Add `MultiSelect`: a one-line dropdown with removable selection chips,
overflow count, clear-all and immediate independent selection.

**Current behavior:**

The public roster has no compact multiple-selection control. Select chooses one
value, Choices is a single-selection radio group, Checklist is read-only and Button
has no checked/pressed contract. Source inspection confirmed this at `2235675`
(package 3.8.0); all 52 existing Select, Choices and Checklist tests passed. No
matching prior rejection was found. The consumer needs 12 options in its Songs
filters, with app-owned OR/AND semantics.

**Desired behavior:**

Give MultiSelect the ordinary labelled dropdown appearance of Select, with a
dropdown arrow. The control always occupies one line. Selected options appear as
individually removable chips; show the leading chips that fit in supplied option
order, followed by `+N` for the remaining selected options. Reserve room for the
count, clear-all and dropdown controls. Recalculate overflow on width and label
changes without changing selection. Long chip labels may truncate visually, but
their full names remain accessible. At narrow widths, a count-only selection
display is allowed; never wrap chips or widen the surrounding page.

Opening presents a single column of checkable options anchored to the control.
The surface floats without moving the page and stays within the available viewport,
including opening above when necessary; its options can scroll vertically. Use the
shared floating elevation role. All options remain reachable, including options
represented only by the overflow count. Activating the count opens the same dropdown.

Each toggle, chip removal and clear-all requests its change immediately. The
dropdown stays open while selecting. There is no Apply/Cancel stage; opening and
closing never change selection. A clear-all control appears when the selection is
nonempty and requests the empty set, including selections hidden by overflow.
Chip removal and clear-all do not accidentally open or toggle the dropdown.

**Key interfaces and ownership:**

- Export one `MultiSelect` roster entry. A compound namespace is allowed; its
  exact member structure is an implementation choice within this contract.
- Required `selected$: Observable<readonly string[]>` supplies the current set of
  selected identities; required `onChange$: Subject<readonly string[]>` emits a
  fresh full proposed selection for each user edit, with no duplicate identities,
  ordered by supplied option order. Never mutate incoming arrays.
- Render selection from the latest input emission; do not maintain an independent
  optimistic selection. The consumer feeds accepted changes back into `selected$`
  immediately for normal interaction. An unanswered request leaves selection
  unchanged. Before a source first emits, render empty; on source replacement,
  discard the old source's selection and wait for the new one. Recommend a
  replaying state source in usage examples so remounting restores current state.
- Subscribe only to the input, unsubscribe on replacement/unmount, never complete
  either stream or define their error/completion policy. Programmatic state
  emissions, rendering, option updates and source replacement emit no `onChange$`.
- Options have unique stable string identities and caller-authored labels.
  Reordering or translation preserves selection by identity. The consumer must
  remove unavailable identities from selection when it removes their options in
  the same logical update; stale identities violate that contract. Do not emit
  synthetic changes or silently rewrite selection to reconcile invalid input.
- Require a visible label and caller-authored empty-selection wording. Supply all
  other text from the consumer too: option labels, removal accessible names,
  clear-all accessible name, optional help and overflow wording. Support the
  dynamic hidden count with a documented closed wording contract, without React
  callback props or built-in English. Show an English and a German example.
- Supply a whole-control `disabled` state and the usual `testId` hook. Disabling
  retains the visible selection, closes an open surface and prevents all user
  changes. Input state can still update a disabled control. No per-option disabled
  state is required; unavailable options are omitted by the consumer.
- This first capability is a consumer-controlled selection control. Native form
  submission/reset, required-selection validation and domain filtering rules are
  not added as part of this proposal.

**Keyboard and accessibility contract:**

- Associate the visible label with the dropdown trigger and name the option group.
  Expose expanded/collapsed state and each option's name and checked state. Use
  checkbox-equivalent independent selection semantics, not radio or menu-action
  semantics. Selection has a visible mark independent of colour.
- Enter, Space or ArrowDown on the closed trigger opens the dropdown and focuses
  the first selected option in option order, or the first option if none is
  selected. With no options, focus stays on the trigger.
- Tab/Shift+Tab traverse available controls and options normally; Space toggles a
  focused option. Do not trap focus. Leaving the whole control by keyboard closes
  the surface and preserves the new focus destination.
- Escape closes and returns focus to the trigger. An outside pointer interaction
  closes without stealing focus from its destination. The trigger also closes an
  open surface. None of these operations emits a selection change.
- Chip removals and clear-all are keyboard-operable, named controls; do not nest
  interactive buttons inside the dropdown trigger. If a successful removal makes
  its focused control disappear, move focus to the next visible chip removal,
  then the preceding one, or the trigger if none remains. Clear-all returns focus
  to the trigger when its own control disappears. Focus must not fall to the body
  when overflow recalculation hides a focused chip; return it to the trigger.
- Use the shared focus treatment in both themes. Document disabled and empty-option
  behavior, and ensure long translated option labels remain readable in the list.

**Acceptance criteria:**

- [ ] Public package consumers can select zero, one, several or all options
  independently through MultiSelect; other selection components retain their contracts.
- [ ] A consumer that feeds back user changes sees each toggle, chip removal and
  clear-all immediately, with exactly one output event per edit and no Apply step.
- [ ] The closed control stays on one line for 12 selected options, long translated
  labels and narrow widths. `+N` counts hidden selections accurately after resize,
  translation, removal and option reorder; every selection remains reachable.
- [ ] External restore and clear update chips and checks silently, including while
  the dropdown is open or the control is disabled. Consumer reconciliation of
  removed options does not emit another user change.
- [ ] Tests cover ignored requests, repeated toggles, nonmutated input arrays,
  initial/source-replacement behavior, subscription teardown and remount restoration
  from a replaying source. No completed or errored stream policy is added.
- [ ] Pointer, touch and keyboard users can open, toggle, remove, clear and dismiss.
  Tests cover names, checked/expanded states, focus return, Tab departure and disabled
  behavior. Clear/removal controls never trigger a surrounding form submission.
- [ ] Tests exercise the public behavior through DOM and stream boundaries, following
  the repository's test-first standard. No assertions on recipe strings or private
  state. Use controlled measurement boundaries where jsdom lacks layout.
- [ ] Stories cover empty, one, multiple, all, overflow, narrow widths, long English
  and German labels, clear/restore, disabled and option updates. Inspect actual
  wrapping, overflow, viewport placement and focus in Storybook in both themes;
  jsdom alone cannot prove these layout properties.
- [ ] Keep a closed prop surface, semantic tokens, one recipe per painting member,
  consumer-owned wording and RxJS ownership. No styling/HTML attribute escape hatches.
- [ ] Lint, typecheck, tests, package build and Storybook build pass. Document the
  public contract, caller obligations and usage. Carry the agreed MultiSelect term
  into the domain glossary if the implementation checkout does not already contain it.
- [ ] The normal release process publishes the capability; record the actual released
  package version on #110. A merged implementation alone does not unblock the
  consumer upgrade; do not claim publication before verifying it.

**Out of scope:**

- Search, async option loading, virtualization, creatable values, grouping, select-all,
  a filter builder or game-specific semantics.
- Standalone public Checkbox, Popover or Chip components, and changes to the existing
  Select/Choices contracts.
- Wrapping chips, a multiline closed control, the prototype's two-column panel,
  staged Apply/Cancel selection, or automatic pruning of consumer state.
- Native form integration, validation rules, persistence owned by the component,
  React callback props or a translation framework.
