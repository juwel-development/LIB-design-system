## Agent Brief

**Category:** component-proposal (enhancement)
**Summary:** Add optional stable column allocations and per-table density to Table, leaving content adaptation with cell contents and residual overflow with Table's #114 scrolling contract.

**Current behavior and verification:**
Source inspection of Table's public props, implementation, tests and Storybook examples confirms that it has no column-definition or density contract. Cells support alignment and value/note treatments. Root requires a caption, headers require explicit scope, and column widths follow content. With notes omitted, Root provides a keyboard-reachable horizontal scroll region; supplementary notes hide below 48rem and content notes stack rows. Existing stories do not demonstrate stable column allocation with long translated comparison content.

Redundancy checks covered Table, theme sources and other public component implementations for column sizing, density and wrapping. No equivalent public column-allocation API was found. The accepted #114 brief provides automatic horizontal overflow across notes modes; it does not provide responsive column allocation. The consumer specification is [Label Manager #195](https://github.com/juwel-dev/g-label-manager/issues/195). These are verified missing public contracts from source inspection, not a reproduced browser defect; runtime verification remains implementation work.

The prior-rejection knowledge base contains no rejection of this capability. Figure-width and Brandmark-size decisions caution against inventing size vocabularies. ADR 0008 now records the maintainer's explicit table-specific sizing decision and narrow density exception. Preserve the closed prop surface and semantic token contract.

**Accepted behavior:**
- Consumers may declare columns once on Table.Root, in the order used by header and body cells. Every row shares the same allocation; cells do not repeat widths.
- A definition selects either a fixed token-defined width or a positive relative proportion, and may supply a token-defined minimum width. Fixed and proportional columns can coexist.
- Filtering, sorting, paging, long content, empty results and content updates do not change allocations while the definitions, theme, density and available table width remain the same. Available width changes may redistribute proportional space. Explicit consumer definition changes and theme changes may change allocations.
- Fixed columns retain their allocation. Proportional columns share the remaining available space according to their weights, subject to minimums. If a minimum constrains a column, redistribute the remaining space among unconstrained proportional columns. Minimums are floors; a fixed width smaller than its minimum resolves to the minimum. All-fixed tables do not stretch their columns just to fill unused space.
- Components inside cells own their wrapping and adaptation. Table does not resize descendant controls, truncate labels, hide essential content or change column allocation in response to intrinsic content width. Ordinary text may wrap. Residual overflow remains reachable through Table's #114 horizontal scrolling; it must not overlap adjacent cell content or cause page-wide overflow. Use representative content and appropriate allocations/minimums to prove the composition works.
- Explicit definitions preserve a comparison table at narrow widths: no automatic note-column hiding or row stacking, including when notes is supplied. Note typography remains available. This is an opt-in change to responsive behavior.
- Omitting column definitions preserves content-driven sizing and existing responsive note behavior, together with #114's universal residual horizontal overflow handling.
- Density is selected independently per table: `comfortable` is the default and preserves existing cell spacing; `compact` reduces cell padding. Both use theme-defined tokens. Neither changes font sizes or descendant control dimensions. Header and body cells use the selected density consistently.

**Key interfaces and implementation latitude:**
- Table.Root gains optional ordered column definitions and `density?: 'comfortable' | 'compact'`. Use a closed discriminated definition for fixed versus proportional allocation, with an optional minimum token reference. Preserve children composition, captions and explicit header scope.
- Fixed/minimum token references must use the library's typed semantic-token mechanism. Establish and document the smallest role vocabulary justified by representative consumer columns; exact identifiers and default measurements are implementation choices, not a new size ladder. Theme changes must affect the rendered allocation. No arbitrary CSS strings or consumer className/style forwarding.
- Keep the allocation contract independent of current row content and avoid a data-array/sorting API. Specify how definitions correspond to cell order and document the required consistent column count. Existing spanning/complex-header capabilities need not be expanded.
- Interactive resizing is deferred. Preserve the agreed extension direction: a future consumer-controlled runtime width can replace a proportional allocation with a fixed one; other proportional columns share the remainder. Do not implement a speculative runtime numeric override API, drag handles, keyboard resizing or persistence in this ticket.

**Acceptance criteria:**
- [ ] Public examples demonstrate fixed-only, proportional-only and mixed definitions, optional minimums and consistent header/body alignment. A 3:1 unconstrained allocation follows that ratio; constrained columns respect their minimums and remaining space is redistributed predictably.
- [ ] Browser checks show stable column boundaries while filtering, sorting, paging and updating short/long content under unchanged allocation inputs. Include empty results and subsequent repopulation. Resizing the available table space redistributes proportional widths without changing fixed widths or violating minimums.
- [ ] At insufficient width, fixed/minimum allocations remain intact and the Table scroll surface from #114 makes overflow accessible without page-wide horizontal scrolling. Include non-wrapping controls, long English/German labels and long unbroken content; prove content neither overlaps neighboring columns nor becomes unreachable.
- [ ] With explicit definitions, supplementary and content note modes retain all columns and tabular rows at narrow widths. Without definitions, their established hide/stack behavior remains compatible.
- [ ] Caption, header associations, semantic table structure, row/column order, keyboard access and visible focus remain valid. Composed actions and #113 row interactions remain independent; allocating space adds no sorting, selection or activation behavior.
- [ ] Comfortable is the default, matching previous padding. Compact can coexist with comfortable on the same page; theme tokens control both treatments. Density does not change typography or dimensions declared by descendant controls. Verify keyboard focus visibility and representative action cells in both treatments.
- [ ] Public typings constrain column definitions and token references and retain the closed surface. Document valid positive proportions, minimum precedence, column-order correspondence, content responsibility, overflow behavior and compatibility when definitions are omitted.
- [ ] Add public behavior tests and Storybook examples at broad and narrow desktop/laptop widths, with long translated labels, composed controls and enough rows to show comparison stability. Follow repository test-first standards for implementation. Use real browser geometry/interaction checks for sizing and overflow; DOM tests alone do not prove layout.
- [ ] Run required formatting, lint, type checks, tests, package build and Storybook build. Keep public contracts, theme token documentation and ADR statements consistent with the accepted decisions.
- [ ] Publish through the normal release process and record the actual released version in consumer #195. Report implementation and publication separately; triage itself does not publish a release.
